DEX 与 AMM 是什么？

从中心化交易所到智能合约流动性池

CEX

中心化交易所

  • ● Binance、OKX、Coinbase
  • ● 订单簿撮合（Order Book）
  • ● 资金托管在交易所
  • ● 需要 KYC、实名认证
  • ● 速度快，流动性深
  • ✗ 单点故障 · 不可审查 · 信任第三方
DEX

去中心化交易所

  • ✓ Uniswap、Curve、Balancer
  • ✓ AMM 公式驱动（无订单簿）
  • ✓ 用户保留资产控制权
  • ✓ 无需 KYC，完全 permissionless
  • ✓ 24/7 运行，不可被关闭
  • ⚠ 智能合约风险 · MEV 暴露 · 更高 gas

订单簿是怎么工作的？（先理解 CEX，再理解为什么链上行不通）

以 Binance 上 ETH/USDC 为例。买方挂"买单"（Bid），卖方挂"卖单"（Ask）。 交易所维护一张实时列表，按价格排序： 

── 卖方（Ask，从低到高）──────────────────
卖 1.0 ETH  @  $2,005   ← 最低卖价（ask）
卖 2.5 ETH  @  $2,008
卖 0.5 ETH  @  $2,010

── 中间：买卖价差（spread = $5）────────

── 买方（Bid，从高到低）──────────────────
买 0.8 ETH  @  $2,000   ← 最高买价（bid）
买 3.0 ETH  @  $1,998
买 5.0 ETH  @  $1,995

当你下一笔"市价买单 1 ETH"，交易所立刻用 $2,005 的卖单和你成交——这叫撮合（matching）。 那些持续挂单、维持买卖两侧流动性的人，叫做做市商（Market Maker）。 他们每天挂撤数千笔单，赚取微小的买卖价差，是交易所流动性的核心来源。

为什么链上不能用订单簿？

在 Binance 上，你挂一个买单"1 ETH @ $1,999"，不花钱，随时可以撤单。 但在以太坊上，每一笔操作（挂单、撤单、成交）都是一次链上状态变更，都要消耗 Gas 费，约 $2–$15/笔。

做市商每天挂撤几百笔单才能赚到微薄的价差。在链上做这件事：每次撤单 ~$5 gas， 每次成交 ~$10 gas，一天下来 gas 成本轻松超过收益，做市商会直接亏损。 没有做市商 = 没有流动性 = 交易所无法运作。

更糟糕的是：以太坊出块约每 12 秒一次，期间所有新交易都排队等待。 高频做市策略（毫秒级）在这个延迟下根本无法运转。

结论：链上需要一个不需要做市商、价格由数学公式自动决定的机制。 这就是 AMM（Automated Market Maker，自动做市商）的诞生背景。 AMM 用一个数学不变量代替订单簿——任何人随时可以与公式交互，无需对手方。

Uniswap V2：x · y = k

恒定乘积公式的原理与推导

直觉理解：跷跷板模型

想象一个跷跷板，左边放 ETH，右边放 USDC。当有人向池子里加入 ETH（左边变重）， 右边的 USDC 必须减少来保持"乘积"不变——就像跷跷板保持平衡一样。

关键性质：池子永远不会被掏空。 当 ETH 储备趋向于 0 时，你需要支付无穷多的 USDC 才能再买走哪怕 1 wei 的 ETH—— 数学上阻止了完全榨干。这是恒定乘积曲线（双曲线）的核心保证。

另一个直觉：池中 ETH 的边际价格（再买 1 个 ETH 的瞬时成本）= USDC储备 / ETH储备 = y/x。 买入 ETH 后，x 减小、y 增大，所以价格上涨——你买得越多，每个 ETH 越贵。这就是价格影响（Price Impact）。

核心不变量

x · y = k

其中 x = Token A 储备量，y = Token B 储备量，k = 常数（每次交易后保持不变）

初始状态示例：
池中有 1,000 ETH 和 2,000,000 USDC
k = 1,000 × 2,000,000 = 2,000,000,000
当前价格 = y / x = 2,000,000 / 1,000 = $2,000 / ETH

0.3% 手续费的工作原理

手续费不是事后加到交易结果上的，而是内嵌在不变量检验中：

Δy = y · (Δx · 0.997) / (x + Δx · 0.997)

合约实际检查的条件是：

(x + Δx · 0.997) · (y − Δy) ≥ k

实际上只有 99.7% 的输入量参与定价计算，剩余 0.3% 留在池中作为手续费， 使得 k 实际上略微增大——LP（流动性提供者）的份额价值随每笔交易而增加。

逐步推导：买入 10 ETH 的完整计算

初始池：x = 1,000 ETH，y = 2,000,000 USDC，k = 2,000,000,000
我想买入 10 ETH，需要支付多少 USDC？ 

// 我是买方：想得到 Δx = 10 ETH，付出 Δy USDC
// 使用公式：(x - Δx) · (y + Δy · 0.997) = k

// 第一步：新的 ETH 储备
x' = 1,000 - 10 = 990 ETH

// 第二步：从不变量解出新 USDC 储备
x' · y' = k
990 · y' = 2,000,000,000
y' = 2,000,000,000 / 990 = 2,020,202 USDC

// 第三步：需要支付的 USDC（含手续费前）
Δy_raw = y' - y = 2,020,202 - 2,000,000 = 20,202 USDC

// 但这是手续费后的等效量，换算为实际支付：
Δy_actual = 20,202 / 0.997 ≈ 20,263 USDC

// 简化公式直接计算（等效，更常用）：
Δy = (y · Δx) / ((x - Δx) · 0.997)
   = (2,000,000 × 10) / (990 × 0.997)
   ≈ 20,263 USDC

// 有效价格（每 ETH 实际花费）
有效价格 = 20,263 / 10 = $2,026.3 / ETH

// 价格影响
影响 = (2026.3 - 2000) / 2000 = +1.32%

合约视角：swap() 函数内部发生了什么

当你点击 Uniswap 界面的"Swap"按钮，背后调用的是 UniswapV2Pair.swap()，流程如下：

// 第 1 步：用户调用，指定想要收到多少代币
pair.swap(amount0Out=10 ETH, amount1Out=0, to=用户地址, data=0x)

// 第 2 步：合约先把代币发给用户（"先给后检查"）
IERC20(ETH_token).transfer(用户地址, 10 ETH)

// 第 3 步：读取当前池子储备（此时用户的 USDC 已经转入合约）
balance0 = ETH_token.balanceOf(address(this))   // = 990 ETH
balance1 = USDC_token.balanceOf(address(this))  // = 2,020,263 USDC（含用户转入）

// 第 4 步：计算有效输入量（减去本次输出，剩余增量就是输入）
amount1In = balance1 - (reserve1 - 0)  // = 20,263 USDC

// 第 5 步：验证不变量（含 0.3% 手续费扣除）
require(
  (balance0 · 1000 - amount0In · 3) · (balance1 · 1000 - amount1In · 3) ≥ reserve0 · reserve1 · 1000²
)
// 若不等式不成立 → revert，交易回滚，用户损失 gas 但资产归还

// 第 6 步：更新储备变量
reserve0 = balance0  // 990 ETH
reserve1 = balance1  // 2,020,263 USDC

注意"先给后检查"的设计：合约先把代币发出去，再验证对方是否付款足够。 这个设计让 Flash Swap（闪电贷）成为可能——后面会详细讲。

LP Token 与无常损失

做流动性提供者能赚到什么？又会损失什么？

如何成为流动性提供者（LP）

  1. 按当前比例存入两种代币（如 1 ETH + 2,000 USDC）
  2. 获得 LP Token（代表你在池子中的份额百分比）
  3. 交易者每笔交易付 0.3% 手续费，按份额比例分配给所有 LP
  4. 随时可以销毁 LP Token，取回代币 + 累计手续费收益
首次 mint：L = √(x · y)
后续 mint：L = min(Δx/x, Δy/y) · Ltotal
具体示例：Alice 做 LP

池子当前：10,000 ETH + 20,000,000 USDC，LP Token 总量 = 10,000 个。
ETH 当前价格 = $2,000。

Alice 存入 1 ETH + 2,000 USDC（总值 $4,000）。
她获得的 LP Token = (1/10,000) × 10,000 = 1 LP Token（占总量 0.01%）。

三个月后，这个池子累计收取了 $600,000 手续费。
Alice 的份额 = 0.01%，分得 $60 手续费。
但这三个月 ETH 价格从 $2,000 涨到了 $4,000——这里有陷阱，见右侧。

无常损失（Impermanent Loss）

为什么会有无常损失？直觉理解

当 ETH 从 $2,000 涨到 $4,000，套利者会注意到： Uniswap 池中的 ETH 还在以旧价格定价（便宜了），于是大量买入池子里的 ETH， 直到池子里的价格追上市场价 $4,000。

这个过程结束后，池子里的 ETH 减少了（被套利者买走），USDC 增加了。 LP 被迫以平均低于市场的价格卖出了部分 ETH——这就是无常损失的本质。

如果你不是 LP，只是直接持有（1 ETH + 2,000 USDC），你的 ETH 还是 1 整个， 可以在市场上卖 $4,000。但 LP 的 ETH 已经被套利者"换走"了一部分。

完整计算：Alice 的无常损失

初始状态：Alice 存入 1 ETH + 2,000 USDC，ETH = $2,000，总值 $4,000。

设 Alice 占池子 1%（简化计算）。初始池：100 ETH + 200,000 USDC。

// ETH 翻倍到 $4,000，套利后池子重新均衡
// 不变量：x · y = k = 100 × 200,000 = 20,000,000
// 新均衡：y/x = 新价格 = 4,000
// 联立：x · 4000x = 20,000,000 → x² = 5,000 → x = 70.71 ETH

新 ETH 储备  = √(k / 新价格) = √(20M / 4000) = 70.71 ETH
新 USDC 储备 = √(k × 新价格) = √(20M × 4000) = 282,843 USDC

Alice 取回（1% 份额）：
  ETH:  70.71 × 1% = 0.7071 ETH（价值 $2,828）
  USDC: 282,843 × 1% = 2,828 USDC

LP 总价值   = $2,828 + $2,828 = $5,657
直接持有价值 = 1 ETH × $4,000 + 2,000 USDC = $6,000

// 无常损失（绝对值）
IL = $5,657 - $6,000 = -$343（-5.7%）

也就是说，即使 ETH 涨了一倍，当 LP 的 Alice 比直接持有少赚了 $343。 如果手续费收入超过 $343，还是值得做 LP；否则不如直接持有。

IL = 2√r / (1+r) − 1

其中 r = P新 / P初始（以上 r=2 时，IL = 2√2/(1+2)−1 ≈ −5.7%，与计算吻合）

Flash Swap（闪电贷）

无抵押借贷：原理、正当用途与攻击场景

机制：原子性是关键

  1. 调用 swap()，请求任意数量代币（无需提供抵押）
  2. 池子立即将代币转入你的合约
  3. 你的回调函数 uniswapV2Call() 执行任意逻辑
  4. 同一交易结束前，必须归还代币 + 0.3% 手续费
  5. 若还款不足，整笔交易 revert——原子性保证安全
为什么"无抵押"是安全的？
因为借贷和还款发生在同一笔以太坊交易内。 以太坊的"原子性"（atomicity）保证：要么这笔交易里所有操作全部成功， 要么全部回滚。如果你借了 1000 ETH 却没还，整笔交易回滚， 那 1000 ETH 从未真正离开过池子——从链的角度看，什么都没发生。

Uniswap V3：集中流动性

V2 资本效率问题与 V3 集中流动性的解决方案

V2 的资本效率问题

真实数字：$100M 池子里到底有多少在工作？

假设 Uniswap ETH/USDC 池中有 $100M 流动性。
ETH 价格 90% 的时间在 $1,000–$3,000 之间。
V2 把这 $100M 均匀分布在 $0 → ∞。

价格在 $1,000–$3,000 区间时，实际工作的资金：
  有效比例 ≈ (√P_high − √P_low) / √P_high
           = (√3000 − √1000) / √3000
           = (54.77 − 31.62) / 54.77
           ≈ 0.0423  （约 4%）

只有约 $3–5M 的流动性在参与交易！
剩下 $95–97M 在"睡觉"，产生零收益。

对 LP 来说，资本效率低意味着什么？

手续费收益率直接取决于有多少资金真正参与了交易。

如果同样的 $10,000 在 V3 集中区间内能挣 $50/天，
在 V2 只能挣 $1/天——因为大部分资金不在有效区间，不会累积手续费。

V3 的集中流动性，本质上是把闲置资本"激活"，让每一分钱都去赚手续费。

为什么用对数（log）刻度而非线性刻度？

价格范围跨越 $0.001 到 $100,000，跨越了 8 个数量级。

用线性刻度：在 $1 附近，一个 tick 只有 $0.000001 的精度； 在 $100,000 附近，同一个 tick 却代表 $0.1 的精度——精度极度不均匀， 高价格区间会浪费大量存储空间。

Flash Accounting

V3：每步操作都转移代币（ERC-20 transfer = 昂贵的 SSTORE）
V4：在内存中追踪 delta，最后统一结算

三步操作只产生 2 次代币转移

操作 1 — swap USDC→ETH：
  delta[USDC] -= 1,000    delta[ETH] += 0.5

操作 2 — add liquidity：
  delta[ETH]  -= 0.3     delta[USDC] -= 600

操作 3 — swap ETH→USDC：
  delta[ETH]  -= 0.1     delta[USDC] += 230

─────────────────────────────────────────
净 delta：
  USDC: −1,000 − 600 + 230 = −1,370 USDC
  ETH:  +0.5 − 0.3 − 0.1 =  +0.1 ETH

V4 安全风险：Hooks 的代价

可编程性越强，攻击面越大

Hook 攻击面分析

  • 访问控制缺失：Hook 的回调函数如果没有限制只能被 PoolManager 调用， 攻击者可以直接调用 beforeSwap()，绕过池子的正常流程， 伪造 delta 或榨干流动性。
  • 恶意 Hook：用户无法区分"善意 Hook"与"吸血 Hook"。 一个看起来提供动态手续费的 Hook，可能在 afterSwap() 中悄悄转走部分代币。 池子创建者完全控制 Hook 逻辑，用户只能信任或不信任。
  • Share 舍入攻击（Donation Attack）：攻击者作为第一个 LP 存入极小量（如 1 wei），然后直接向池子 donate 大量代币， 使每股 LP 价值暴涨。后续 LP 存入时因舍入误差， 会少拿到流动性份额——本质是 ERC-4626 的 inflation attack 变体。
  • 重入风险：Flash Accounting 在单笔交易内允许多次回调， 若 Hook 内部再次调用池子的操作，可能触发意外的重入状态。

已发现的具体漏洞

int128 类型强制转换漏洞

V4 PoolManager 早期代码中，delta 值被存储为 int128， 但在某些 Hook 返回路径中，未检查累积 delta 是否溢出 int128 范围 （约 ±1.7×1038）。理论上可通过构造极端 Hook 返回值 使 delta 发生整数溢出，导致用户获得超额代币。

原生 ETH 处理漏洞

V4 支持池子直接使用原生 ETH（而非 WETH）。 早期实现中，settle() 函数在检查原生 ETH 余额时 存在逻辑缺陷：如果 Hook 在回调期间向合约发送 ETH， 可以使结算时的余额校验通过，而实际上用户欠款未清。 Uniswap 安全团队在审计阶段发现并修复了此漏洞，未在主网发生。

⚠️ V4 于 2025 年 1 月主网上线，目前 TVL 正在快速增长但 Hook 生态仍在早期。 使用任何 Hook 池之前，确认 Hook 合约已通过独立审计。
对开发者的建议： 部署 Hook 时，务必在 beforeSwap / afterSwap 等函数开头加 require(msg.sender == address(poolManager))，防止未经授权的直接调用。

真实攻击案例

理解漏洞比背记更重要

案例一（最重要）

Balancer V2 精度损失漏洞

$128,000,000 2025年11月3日 · 30分钟 · 6条链

首先理解：Balancer Stable Pool 的不变量 D

普通 Uniswap 的不变量是 k = x·y（乘积恒定）。 Balancer Stable Pool 用更复杂的公式，以稳定币三池（n=3）为例：

A·nn·S + D = A·D·nn + Dn+1 / (nn·P)

其中 S = 各代币储备之和，P = 各代币储备之积， A = 放大系数（Amplification Coefficient），n = 代币数量。 D 是满足上述方程的唯一正实数——它代表"如果所有代币完全等价，池子的总价值"。 D 通过牛顿迭代法（Newton's method）数值求解，每次迭代都依赖当前储备精度。

关键：BPT（Balancer Pool Token）的价格直接由 D 决定：

PBPT = D / SBPT

其中 SBPT 是 BPT 的总供应量。D 越大，每个 BPT 越值钱；D 被压低，BPT 就被低估。

攻击核心逻辑：如果攻击者能人为压低 D 的计算值， 就能以人为压低的价格购买 BPT，然后用真实价值赎回底层资产—— 差价就是攻击利润。漏洞的作用正是让 D 在每次迭代中被系统性地低估。

根因：一个舍入方向错误

Balancer Composable Stable Pool 的 _swapGivenOut() 函数在对代币数量进行"精度缩放"时，使用了 mulDown()（向零截断）：

- return FixedPoint.mulDown(amount, scalingFactor);
+ return FixedPoint.mulUp(amount, scalingFactor);

在 GIVEN_OUT（指定输出量）语境中，协议计算"我需要多少输入才能输出 X？" 答案应该向上取整（让用户多付一点），保护协议不亏。 使用 mulDown 等于协议少收了代币，每次都在亏微小的一点。

精度损失的数学

正确行为（mulUp）
8 wei × 1.114×1018 = 8.912×1018 → 向上取整 = 9 wei
协议收到 9 wei — 正确，略微保守 ✓
漏洞行为（mulDown）
8 wei × 1.114×1018 = 8.912×1018 → 向下截断 = 8 wei
协议少收 1 wei（误差 ~10.2%）✗
攻击者策略
重复执行 10,000 次 → 每次损失 ~10% → D 被迭代压低
BPT 价格人为降低 → 低价回购 → 套利获利
为什么误差这么大？ 因为攻击者先把池子的储备量从 ~1018 级别 降至 ~101 级别（只剩 8 wei）。在极小数值下，整数截断误差占比极大。 普通规模的交易不会触发这个问题——这是攻击者精心设计的前置条件。

攻击时间线（30 分钟，6 条链）

  1. 闪电贷获取大量 BPT，将其换回底层 LSD 资产（rETH、cbETH、wstETH）
  2. 排干池子储备量：通过大量单向交换，将池中各代币余额从 ~1018 wei 压至 ~101 wei（仅剩几 wei）
  3. 反复触发精度漏洞：以 amount = 8 wei 的微小交易循环调用 _swapGivenOut()，每次调用都使 D 被低估约 10%
  4. 迭代压低 D：经过 ~10,000 次循环后，D 的计算值已远低于真实值，BPT 价格被人为压低
  5. 大量回购 BPT：在被压低的假价格下买入大量 BPT
  6. 赎回获利：用真实价格赎回底层资产，套利差价即为利润
  7. 跨链重复：在 Ethereum、Polygon、Arbitrum、Optimism、Avalanche、Gnosis 6 条链上依次执行，历时不足 30 分钟
为什么能跑遍 6 条链？ Balancer 在各链部署的是同一份合约代码。漏洞是编码级别的， 跨链部署意味着每一条链都有同样的漏洞，攻击者系统性地逐链收割。

亲手体验精度损失：迭代累积效应

① 单次 mulDown 截断
② 攻击者循环 N 次后累积效应
核心教训：在 Solidity 定点数运算中，舍入方向不是"无关紧要的细节"， 而是协议安全的基础。对于"协议收多少"的场景永远 mulUp， 对于"用户收多少"的场景永远 mulDown。方向反了，攻击者就能无限套利。
案例二

KyberSwap Elastic Tick 边界 Bug

$47,000,000 2023年11月23日

复习：Tick 边界是什么？（回顾第三节）

在 Uniswap V3（及其 fork）中，价格轴被离散化为一系列 Tick， 每个 tick 对应价格 1.0001i。每个 LP 头寸只在 [tick_lower, tick_upper] 区间内提供流动性。

当价格穿越某个 tick 边界时，合约必须"跨越（cross）"这个 tick： 将该区间的流动性从"活跃"切换为"非活跃"（或反向加入）， 同时更新全局流动性变量 liquidity。 这个"跨越"动作是集中流动性模型中逻辑最复杂的部分。

KyberSwap 的 computeSwapStep() 函数负责计算"这一步 swap 能走多远"。 它需要判断：这次 swap 是否会恰好跨越下一个 tick 边界？ Off-by-one 漏洞就藏在这个判断里。

Off-by-One：边界处的双计数漏洞

// 简化的 computeSwapStep 伪代码
if (swapAmount >= amountSwapToCrossTick) {
    // 认为"已跨越"：调整流动性，跨越 tick
    crossTick();
    liquidity += liquidityNet;  // ← 正常路径
} else {
    // 认为"未跨越"：留在当前区间继续计算
    // 但当 swapAmount == amountSwapToCrossTick - 1 时……
    // 内部计算却按"已到边界"处理，再次加上 liquidityNet！
    liquidity += liquidityNet;  // ← Bug：double-count！
}
当 swapAmount = amountSwapToCrossTick − 1 时： 代码进入了"未跨越"分支（以为没有跨越 tick）， 但内部的数值计算却按"已跨越"处理了流动性变化。 结果：liquidity 被计算了两次（double-counted）， 池子里凭空多出一倍的"虚假流动性"。 攻击者随即用这些虚假流动性提取了真实资产。

攻击者针对流动性极稀疏的 tick 范围（空 tick 区间）的池子， 精心构造 swap 序列，精确控制每笔 swap 的金额，让程序反复进入这个特殊分支， 把所有 tick 区间的流动性逐一榨空，最终提走所有底层资产。

教训：集中流动性 AMM 的 tick 边界条件涉及"估算量 vs 精确量"的细微差异， 需要形式化验证（Formal Verification）——数学证明，不是测试。 测试覆盖不到所有边界组合，尤其是这种"差 1"的极限条件。
案例三

Curve Finance Vyper 编译器 Bug

$70,000,000 2023年7月30日

漏洞不在业务逻辑，而在编译器本身。

什么是重入攻击（Reentrancy）？

当合约 A 调用外部合约 B（如发送 ETH）时，B 的 receive() 回调函数可以 在 A 的原始函数还没执行完的情况下，再次调用 A 的函数。 如果 A 在转账之前没有更新自己的内部状态（余额）， B 就可以反复"重入"并重复提款，直到把 A 榨干。

CEI 模式（Checks-Effects-Interactions）是防止重入的标准范式： 先做所有检查（Checks），再更新内部状态（Effects），最后才与外部交互（Interactions）。 只要"Effects 先于 Interactions"，重入就无法利用过时的状态。

为什么 Vyper 的命名锁会失效？

Vyper 提供了 @nonreentrant('lock') 装饰器，本意是给函数加一个链上互斥锁： 函数执行前检查锁变量是否为 0，若是则设为 1 并继续执行，结束后归零。 问题在于 Vyper 0.2.15/0.2.16/0.3.0 的编译器实现中， 存在存储槽分配错误： 两个不同函数的 @nonreentrant 锁被分配到了同一个存储槽， 或者锁变量没有被正确初始化。结果：锁"看起来存在"，但在重入时读到的是陈旧或错误的值， 完全无法阻止重入。 

# 攻击执行流（伪代码）
攻击者 → remove_liquidity(amount)
  ├─ Curve Pool: 检查 nonreentrant lock （读到 0，以为安全）
  ├─ Curve Pool: 发送 ETH 给攻击者  ← 外部调用！
  │     └─ 攻击者的 receive():
  │           └─ 再次调用 remove_liquidity(amount)  ← 重入！
  │                 ├─ lock 还是 0（槽被分配错了）
  │                 ├─ 余额未更新，以为还有全额
  │                 └─ 再次提款成功 ✓（第二层）
  └─ 返回第一层，余额更新  ← 已经晚了
# 结果：攻击者提走了 2× 原始金额

如果是 Solidity + CEI 模式，则会在发送 ETH 之前先把余额清零—— 即使重入发生，第二次调用看到余额为零，提款 0，无利可图。
